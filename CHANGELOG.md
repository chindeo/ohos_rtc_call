# Changelog

## Unreleased

- Letters now separate with `;` instead of 、, and long unpunctuated sentences get **up to two** commas inserted at word boundaries — both from the same 2026-10-22 measurement pass (8–16 reps per condition, SenseVoice read-back, then confirmed by ear on the ShiMeta panel). `I;C;U;…` vs `I、C、U、…`: 2481 ms vs 3585 ms for the same phrase, and the semicolon version read back **identically 8/8** while the ideographic-comma one produced **seven** different transcriptions; `JHC` saves 1.26 s, `PICC` 1.35 s. `, . ! ? ： ，` all sit in the 3.3–3.6 s band, so only the semicolon actually helps — **why is unexplained** (`;` is token id 2 in `tokens.txt`, but the letters go through espeak), so it ships on measurement, not on mechanism. For Chinese sentences ≥14 characters with no punctuation, `二十三床患者张三呼叫护士站请尽快前往处理` was **16/16 wrong every time** (dropping 患/三, which the field also heard on device) and drops to 1/16 once two commas go in at word boundaries, costing 0.74 s. Two boundaries came out of the same test and must not be crossed: **never split by character count** (a hard 4-character cut broke 护士站/请 and the model then reordered syllables — "护士战", "情紧快" — 12/12 wrong and 2 s longer), and **never use the semicolon in Chinese** (5 distinct read-backs, and the field heard 往 dropped in 前往处理). Digits get no separator at all: `体温、36.5度` is worse than not cutting (6/12 → 9/12, dropping 六) because it fights `number-zh.fst`. Note the two rules therefore need **different punctuation in the same pipeline**.

- Adds arm64-v8a offline-TTS binaries (`libs/arm64-v8a/{libsherpa_onnx,libsherpa-onnx-c-api,libonnxruntime,libcargs}.so`) for **pure-64 panels**, which the shipped armeabi-v7a set cannot serve at all: the ShiMeta `AIOT-3576E` (api20) reports `abilist=arm64-v8a`, has no `abilist32`, and its userspace is `/system/lib/ld-musl-aarch64.so.1` with an ELF64 `appspawn`. `tools/build-sherpa-shim.sh` now takes an arch argument (default unchanged). Model, `-zh` fsts and `espeak-ng-data` are arch-neutral, so nothing was re-downloaded and no parameter was re-swept. Measured on that board with the sherpa CLI: RTF **0.236–0.358** at 4 threads, SenseVoice reads `体温三十六点五度` and `二十一床正在呼叫` back clean, letters come out as `i c u`. The arm64 `libonnxruntime.so` is upstream's **prebuilt**, and on 32-bit a prebuilt ORT was exactly what failed `dlopen ... symbol not found` inside the HAP namespace — that did **not** reproduce here, so no self-built arm64 ORT is needed. What the HAP did need is `libc++_shared.so` shipped inside the package: on these boards the C++ runtime only exists in `/system/lib64`, which the app namespace cannot resolve, so the shim never loaded (`Cannot read property createAsync of undefined`, and zero `SherpaShim` lines) and the bundled `libcurl_http.so` failed for the same reason. Once it ships: four `dlopen ... ok` + `sherpa symbols bound`, `stage=init ok=true create_ms=6174 noiseScale=1 fsts=3`, six phrases all `attempts=1` at `rtf 0.20~0.39`, and TTS costs **~211MB of RSS** on top of an otherwise-loaded ability (mostly onnxruntime's anonymous heap, only 26MB file-backed) — worth knowing on a 4GB panel. See `docs/tts-models-and-native-build.md`.
- Adds `example/tts-probe`: a single-page HAP whose only job is to answer "does this board actually speak" — no call, MQTT or camera code. It stays silent until someone presses a button (deliberate: field staff test by hand). Two findings worth carrying: a host consuming this HAR **must** declare `@ohos.shimeta` itself (`device/RtcShimetaDeviceAdapter.ets` imports it, it is not an oh-package dependency and not a system module — bed compiles only because it keeps its own `@ohos.shimeta.d.ts`), and the three auto-sign profiles on this machine each pin one bundle name, so borrowing a profile means borrowing its bundle name. `publish-ohos-rtc-call.ps1` now strips `example/tts-probe` from the staged package so its signing material and 143 MB rawfile model can never end up in a HAR.

- Corrects the entry below: **the parameter sweep that justified switching to `matcha-icefall-zh-en` was single-sample.** Re-running each phrase 6–12 times at the same settings and reading the audio back gives 17/18 wrong at `noise_scale=0.2`, then 4/18 (0.5), 9/36 (0.6), 11/36 (0.7), 10/36 (0.8), 5/18 (1.0) and 8/18 (1.3) — the usable band is 25%–31% content errors, not "fixed at 1.0". Two phrase classes fail: `为您自动接听` roughly half the time (字字接听 / 自自动接听 / 赠送接听) and `体温36.5度` about a third (三十四点五 / 三三六点五); `21床正在呼叫` is clean above 0.5. Feeding pre-converted 汉字 with no fst fails at the **same** rate with the same substitutions, so this is model sampling instability — not `number-zh.fst`, not sherpa's Chinese front end, which also means upstream #2847's "fine in the author's python script, broken in sherpa" direction does not apply to our model. No knob is left to try (noise, speed in both directions, silence scale 0.2→0.01, fst on/off, digits via fst vs via 汉字), and there is no upstream record of matcha mis-read digits being fixed; #3683 hit the same prosody problem on a self-trained model. What is left is pre-synthesising high-risk phrases from several good samples, or fine-tuning against a purpose-built acceptance set. Also: letters are now separated with 、 (`I、C、U、三床…`) since field listening judged it clearest — same duration as commas (3.55–3.60 s), because the 1.4 s cost is the letters' own phoneme duration and `silence_scale` cannot compress it (0.2/0.05/0.01 measured 3721/3735/3735 ms; 0 is rejected, the valid range is 0.01–10).

- Made `matcha-icefall-zh-en` the default offline TTS model again, **because the 2026-10-20 morning rollback that demoted it was measuring the wrong thing**: the shipped `DEFAULT_NOISE_SCALE = 0.2` was tuned for `matcha-icefall-zh-baker` and carried over untouched, while the model author's own inference script hardcodes `noise_scale = 1.0`. PC 侧扫参 + SenseVoice 回读 shows 0.2 producing exactly the field complaints — `21床正在呼叫` → "二十一床**正**呼叫", `为您自动接听` → "为您**致赠**接听", `体温36.5度` → "**三十四**点五度" — while 0.667/1.0 renders all three correctly. Upstream issue #2847 is the same report ("the author's python script is fine, sherpa duplicates syllables at punctuation"). `RtcTtsController` now selects model, vocoder (`vocos-16khz-univ.onnx`), rule-fst names (`number-zh/date-zh/phone-zh.fst`) and noise scale from a `profileFor(modelDir)` lookup, so baker stays reachable as a fallback instead of a three-constant edit. Three more parts are load-bearing and were each proved by removing them: the fsts must stay (without them the sentence collapses into English number words), letters must be spelled out with 、 **including a trailing 、 after the last letter** (`I、C、U、三床请到护士站`; the version without the trailing separator glues a stray nasal onto the Chinese, and an unsplit `ICU` gets read as one invented word), and **speech rate is pinned to 1.0 on this profile** — `speed=0.9` mis-reads digits even at the corrected noise scale, so `setSpeed()` now no-ops with `stage=speed value=1 model_locked=true` and the hosts' test page shows the rate the engine really uses. Known-open: a 21-character sentence with no punctuation still drops syllables at any parameter, letters stretch a phrase from 2.1 s to 3.6 s, the 16 kHz vocoder is duller than baker's 22 kHz, and `A10床` reads as "A十床" because the field accepted that. See `docs/tts-models-and-native-build.md`.

- Fixed `hangupAll()` ending only one call: it sent a single `s__apply` built from whatever `sessions` happened to iterate first, and the gateway closes chats by `commonRequest.uuid`, so with two bedsidies calling the host, putting the handset down tore down one and left the other sitting in the call. It now sends one hangup per session, each carrying its own uuid, and keeps `is_all=true` as the marker — the same shape Android uses. Unresolved inbound `c__hangup` also logs `sidHash`/`rtcUidHash` (hashes only) so a hangup that gets dropped for not matching a local session is visible in the field instead of silent. Regression test updated: two sessions → two `applyType=3` messages with distinct uuids.
- Speech rate on the shipping model is now device-verified and **0.9 is the recommended ward value**, which resolves the open question in the entry below: on `matcha-icefall-zh-baker` 0.7 produces no duplicated syllables at all but sounds laboured and stops in the wrong places, 0.9 is smooth and reads better than 1.0, 1.0 remains the fallback for an empty/invalid value. Steps of 0.05–0.1 are audible; 0.01 is not. Both hosts' admin TTS test page now shows the rate the engine is actually using (read-only) and a top-of-page warning that Latin letters cannot be read, which the baker lexicon makes a fact rather than a tuning issue.
- Re-enabled a tunable speech rate, driven by the ward parameter `tts.TextToSpeechSpeechRate`, and **supersedes the "Dropped the tunable speech rate" entry below**: that removal was justified by `speed=0.85` producing "211床正在呼呼叫" — but the model under test then was `matcha-icefall-zh-en`, not the shipping `matcha-icefall-zh-baker`, so the evidence never applied to what is in the field. `RtcTtsController` gained `setSpeed()` (read at synthesis time, so a queued phrase picks up the new value) and the value parsing moved to `tts/RtcSpeechRate.ets` — a separate pure file because the controller imports `libsherpa_onnx.so` and cannot be loaded by Hypium. Anything empty / non-numeric / outside 0.5–2.0 falls back to 1.0, so a ward that types `0` or `7` gets normal speed rather than noise.
- Added the caller-side ringback tone: `audio/RtcRingbackTone.ets` synthesises a 5-second wav (450 Hz for 1 s, silence for 4 s) into `filesDir` and loops it through an `AVPlayer` pinned to `STREAM_USAGE_RINGTONE`, so no audio asset ships and the cadence is three constants. Amplitude is deliberately 0.2 — the microphone is already live during call setup on these devices, and a louder tone leaks out of the speaker into the uplink so the far side hears the beeps. Start/stop is wired by the hosts (invite → `onConnected` / `onEnded` / `onError` / page teardown); it is its own player rather than another `RtcRingtoneController` instance, because `playIncoming`'s busy gate would swallow it.
- Moved the single-channel 16-bit WAV writer out of `RtcTtsController` into `audio/RtcWavFile.ets` (byte-for-byte the same function) so the ringback reuses the field-proven encoder instead of carrying a second header builder.

- Reverted the offline TTS default engine to `matcha-icefall-zh-baker` (Chinese only). Field evidence on .104: `stage=enqueue` shows the text reaching the engine is correct (`text=体温36.5度 fed=体温36.5度`, `text=21床正在呼叫 fed=21床正在呼叫`) while the audio came out as "34.5 度" and "21床正呼叫" — the zh-en model drops and duplicates syllables and, worse, **mis-reads digits**, which for a hospital announcement is a content error, not a taste issue. `matcha-icefall-zh-en` is out of both host projects and kept as a backup for the Latin-letter requirement the hospital does have (`D:\tmp\tts\models\zh-en-from-bed` / `zh-en-from-host`, baker backups alongside). Rolling back means three constants in `RtcTtsController.ets`: model dir, `vocos-22khz-univ.onnx`, and the `-zh`-less `number/date/phone.fst` names; `data_dir` is now only passed when `filesDir/<model>/espeak-ng-data/phontab` exists, so a Chinese-only model simply gets an empty string (the shim maps empty to `nullptr`). See `docs/tts-models-and-native-build.md`.
- Fixed the direction flag being rewritten by later signals, which silently disabled every hangup announcement: `upsertSession` recomputed `session.incoming` from each payload's `from`, but in `c__hangup` that field is whoever initiated the hangup — so after the callee rejected, the calling bedside judged itself the callee. Device evidence: `rtc_hangup_reason reason=rejected notice=对方拒接 incoming=true` (and the same for `timeout` → 无人接听) — the text was recognised and then gated out. Direction is now frozen at session creation; regression tests cover both directions (caller announces, callee stays silent).
- `rtc_signal_recv` now also lists the **top-level key names** of `s__apply` responses and `c__broadcast` payloads (`keys=`, values still not logged): the session key the gateway mints asynchronously has to land in one of those two, and event name plus length was not enough to tell which field carries it. Forensics with the new `rtc_signal_recv` log: a bedside placing a call to the host and letting it be rejected, then letting it time out, produced `c__invite` / `c__sdp` / `c__hangup` on both ends and **zero `c__broadcast`** — the gateway never pushes a status-bearing call record to the caller, so 无人接听 / 对方拒接 could not be announced from that channel at all. The reason is on the wire: `peer_grpc.go` sets `HangUpRequest.Reason = UnwrapErr(e).Error()`, so `RtcSignalPayload` gained `reason`, `rtcHangupReasonText()` mirrors the four codes the announcements need (`timeout`→无人接听, `rejected`→对方拒接, `other_answer`→其他设备接听, `is_calling`→对方忙线中; anything else, including a normal hangup, stays silent), and the controller raises the new `onHangupNotice(text, sessionKey)` **only when this device was the caller** (`session.incoming !== true`), keeping the direction rule from the broadcast path in one place. Hosts only speak: the bedside de-duplicates by session+text, the nurse host logs `host_hangup_notice`. Note this mirrors a few entries of the gateway's own `I10nDefault` table as business copy — it is not a replacement for that table, and if the gateway later starts broadcasting the record both paths fire and the hosts' de-dup keeps it to one phrase. See the `c__hangup` section of `docs/call-broadcast-announce.md`.

- Added the `rtc_signal_recv` line: every inbound signaling message now logs its event name, `status`, `result` text and data length, plus `known=` whether the controller actually has a branch for it (candidate messages are skipped, `rtc_route_candidate` already covers them). Before this, an event name outside register/invite/sdp/candidate/answer/hangup/offline/broadcast was dropped in total silence, so "该念的没念" could not be told apart from "网关压根没发" — the two missing announcements (超时无人接听 / 对方拒接) were exactly this ambiguous. The `data` payload is deliberately not logged: it carries patient names and numbers.
- Announcement text now spells out math symbols (`× ÷ = + −` → 乘 除 等于 加 减) before the engine sees it, because neither Chinese front end has a reading for them and `3+2=5` came out as bare digits. The ASCII hyphen is only treated as 减 between two digits, and the mapping runs after the digit-by-digit rule so a phone number such as `0755-1234567` does not start reading as 零七五五减一…
- Switched the offline TTS model to `matcha-icefall-zh-en` so Latin letters read instead of vanishing: the controller now passes `dataDir` pointing at `espeak-ng-data` itself (sherpa checks `<data_dir>/phontab`), ships `number-zh/date-zh/phone-zh.fst`, and extracts the 355-file espeak tree out of `rawfile` into `filesDir` with a `.extracted` marker so only the first boot pays for it. Consecutive upper-case runs are spelled out with commas (`JHC` → `J, H, C`) before reaching the engine — espeak otherwise reads them as one invented English word, and the comma is what gives each letter an audible break.
- Dropped the tunable speech rate: `generateAsync`'s `speed` stretches phoneme durations (`length_scale = config / speed`) and `matcha-icefall-zh-en` loses alignment when stretched — on .61 `speed=0.85` turned `21床,正在呼叫。` into "211床正在呼呼叫", while 1.0 on .93 stayed clean, and 1.0 was the only value field testing accepted. `RTC_TTS_SPEED_*`, the `filesDir/tts-speed.txt` read/write helpers and both hosts' sliders are gone and the engine hardcodes 1.0; a slower voice has to come from a different model, not from this knob. `DEFAULT_NOISE_SCALE` moved 0.33 → 0.2 (still host-overridable via `RtcTtsConfig.noiseScale`) and `stage=init` keeps logging it.
- Fixed a latent local-camera-preview defect: the reference layout's `ForEach` key omitted the local card's video state, so the mounted subtree was never re-evaluated when the preview track went live, and readiness additionally required a `hasFrame` sample that `readyState === 'live'` alone already implies. The key now carries `localHasVideo`/`localVideoReady`, `isLocalVideoReady()` follows `live` only, and a fresh live track emits media state once at creation instead of waiting for the next signal. Note this is **not** what caused the .61 no-self-view report: rebooting the device fixed that one, and publish was already up (`local_video_track 640x480@15`, `localVideo=live`), so the trigger that day was a wedged capture path — the defect fixed here only bites when the track goes live after the card was already mounted.

- Added `RtcAppVersion.build(versionName, buildTime)`, which formats the register payload's `appVersion` as `v<versionName>_hmos_<yyyyMMddHHmmss>` to match how the Android AAR devices report themselves (`v0.0.17_linux_…`) and replace the `bed_native_webrtc` / `nurse_native_webrtc` role markers; the role stays available as `clientType`, and the build timestamp comes from a `BUILD_TIME` constant each host's build script stamps per variant. Note `systemType` is deliberately untouched: the gateway uses `SystemTypeHmos` to decide whether to base64-wrap the SDP it sends, so switching it is a protocol change, not a label change.
- Exported `combineHttpUrl` from the http module so hosts can log the address the client actually requests. The bedside interceptor used to hand-concatenate `baseURL + url`, which printed `https://hostapp/perm/obtainBedPerms` for a request that was in fact correct — the missing `/` is inserted by `combineHttpUrl`, not by the caller.

- Fixed the rebuilt sherpa NAPI shim never initializing. `SherpaOnnxOfflineTtsZipvoiceModelConfig` was declared two floats short of the v1.12.18 header, which shifted every field after it, so `silence_scale` reached `SherpaOnnxCreateOfflineTts` as `0` and the engine returned null — the bedside only showed "TTS 未初始化". The structs now match `c-api.h` field for field, `max_num_sentences` / `silence_scale` are set explicitly (the C API struct carries no defaults), `Reject()` logs the reason natively and rejects with a real `Error` so hosts no longer see `undefined`, and async work carries a resource name. Verified on .104: `stage=init ok=true create_ms=11404 fsts=3`.

- Fixed the shared WebRTC controller tearing down every active call when the server echoed `c__hangup` for a session that was already removed by a local single-call hangup. The echo guard now runs for every `c__hangup` (previously short-circuited by the terminal policy), and the terminal close-all fallback keeps other sessions whenever the payload carries an identity or more than one call is active. `c__offline` and the last-session close-all semantics are unchanged.
- Known boundary (host-validated 2026-10-15 on .61/.93): a `c__hangup` that carries **no** session identity (`uuid`/`rtcUid`/target number all empty) while exactly **one** call remains still closes the whole group, preserving the `b45dd98` single-call close-on-terminal semantics. Android `RtcInitCall.kt:578` instead skips the close-all whenever any other target exists, ignoring the count. Real traffic always carries an identity, so the echo is caught by the guard first; not aligning now to avoid reintroducing the "single-call UI does not close" regression, to be revisited only if device evidence shows a stale identityless terminal.
- Made `RtcRingtoneController` observable: `playIncoming` / `playUrl` now emit a `ring_local_gate` / `ring_url_gate` line through an optional `configureLogger` callback whenever they skip, start, or the driver refuses, so a server-configured URL ringtone that silently does nothing reports the exact reason (`emptyUrl`, `policyDisabled`, `busy`, `channelDisabled`, `noDriver`, `driverNoUrl`) instead of returning with no trace. Purely additive: no default sink, behavior unchanged when no logger is wired, and the `externalUrlEnabled` default stays `false` (hosts opt in via `configurePolicy`).
- Added the URL ringtone fallback race: `playUrl` can now hand the driver an `onResult` callback that reports `playing` / `error` / `idle`, and when `urlFallbackEnabled` is opted in the controller resets the url player and starts the prewarmed local ring on `error`, refusal, or `urlFallbackTimeoutMs` (default 1200ms) without hearing `playing`. It logs `ring_url_gate result=fallback reason=<io|timeout|refused>`. Disabled by default, so a host whose driver never reports an outcome keeps its current behaviour instead of getting a second ring layered on top. See `docs/ringtone-url-fallback.md`.
- Added offline TTS on sherpa-onnx: the `tts` module, its armeabi-v7a prebuilt native chain (including a self-built onnxruntime 1.16.3 in softfp+NEON for the 32-bit bedside runtime), and `createAsync` / `generateAsync` so loading the model stays off the main thread and no longer trips the lifecycle watchdog.
- Added call-announcement events matching Android: `c__broadcast` payloads that carry `status` are now parsed into `RtcBroadcastHistory` and raised through `onCallHistory` (hold notices keep their existing in-controller handling, everything unrecognised still goes to `onBroadcast`), and `RtcHostCallController` raises `onAutoAnswerNotice` when an incoming session meets `autoAnswer`. The bedside maps these to the sherpa TTS voice: `为您自动接听` with the ring stopped, and `无人接听` only when the history is a timeout for a call this device placed, de-duplicated by `uid`. See `docs/call-broadcast-announce.md`.
- Fixed the URL ringtone fallback never firing under real timing. The pending-fallback intent was a local of `playUrl`, so a driver that resolves `true` first and reports `error`/`idle` a few dozen milliseconds later — which is how `AVPlayer` IO failures always arrive — only set `settled` and cleared the timer, writing the intent into a variable nobody read again: no `result=fallback`, no local ring, total silence. The fallback context is now an instance field, a late report triggers the fallback in place, and `stop()` cancels it so a post-hangup `idle` cannot restart the ring. `docs/ringtone-url-fallback.md` also pins the driver-side `audioRendererInfo` order (url → set renderer in `initialized` → prepare) that hosts must follow to avoid `5400102`.
- Fixed digits being silent in every announcement: the matcha Chinese lexicon only knows pinyin, so `21床,正在呼叫。` came out as "床,正在呼叫". The controller now hands `number.fst,date.fst,phone.fst` to sherpa as `ruleFsts` (the NAPI shim reads a new `ruleFsts` config field instead of hardcoding an empty string, and the shim has been rebuilt for armeabi-v7a softfp). Real-device proof on .99: the same sentence is 1.867s of audio with the fsts and 1.21s without. This replaces the short-lived in-house `normalizeTtsText` so there is only one text-normalization layer; note the trap that made this look like a softfp crash — `--rule-fsts` is the ASR flag, TTS wants `--tts-rule-fsts`, and passing the wrong one exits with RC=255 before anything opens an fst. Missing fst files no longer break init (the engine still starts and only loses number reading), so older hosts that have not shipped them keep working.
- Fixed TTS playback never producing sound. `playWav` called `prepare()` straight after assigning the source and never called `play()`, so the first real-device attempt failed with `current state is not stopped or initialized, unsupport prepare operation` — the same `idle`-vs-`initialized` rule the ringtone path already follows. The player now runs the documented state machine (`fdSrc` → prepare in `initialized` → play in `prepared` → resolve on `completed`), resolves instead of hanging when `stop()` cuts a phrase short, and reads the local wav through `fdSrc` rather than an unverified `fd://` url. `stop()` also bumps a generation counter, so pressing it while a phrase is still synthesizing (the multi-second part the bedside test page used to ignore) cancels that phrase instead of playing it out after the user asked for silence.
- Fixed a single announcement wedging the whole queue for two minutes. The bedside renderer intermittently fails to start (`AudioRenderProxyStart: call failed! error code is -1`), and the player then sits in `playing` until the pipeline drains it — measured at 113s for a 2.31s wav, with `framePosition` never leaving 0. `playWav` now takes the audio duration and watchdogs the promise at `max(3s, duration + 4s)`, releasing the stuck player and retrying once with a fresh one, so the worst case is a 6s gap instead of a frozen queue. Announcements also queue and play out in full rather than pre-empting each other: `stop()` only cancels the phrase in flight (the generation is taken when a phrase starts, not when it is requested), so a hangup-driven stop can no longer swallow a queued call announcement. Clock times and serial numbers are normalized to Chinese words before the engine sees them, because `number.fst` runs first and reads `01177125` as "一千一百七十七万一千二百五" and never leaves `date.fst`/`phone.fst` anything to match; short numbers such as bed and temperature values still go through the fsts.
- Added the TTS取证锚点 `rtc_tts_perf`（纯日志，不改行为）：`stage=init` 带 `create_ms/threads/noiseScale/fsts`，`stage=enqueue|synth|play|skip|stop|fail` 带 `seq/synth_ms/audio_ms/rtf/play_ms/attempts/queue`。之前"没出声"、"播了但听不见"和"队列卡住"在日志上是同一个样子，验收清单里的 RTF 和长时间不失效两项也无从判定。`playWav` 现在返回实际尝试次数以便区分一次过和重试过。
- Added the server-driven ring mute: `RtcServerInfo` now carries `muteRingtone` from the `c__register` success payload (`true` = announce only, no ringtone), and `RtcHostCallController`'s `onRegistered` **signature changed** to pass the parsed `RtcServerInfo` through, since the flag is only known at registration. The package itself applies no default — the product口径 (2026-10-17) is **ring muted unless the gateway sends an explicit `false`**, because the gateway currently omits the field in both switch states; hosts implement it as `server.muteRingtone !== false`. Both hosts store it and gate `playIncomingRingtone` alongside their existing `isPlayRingtone` policy, and the bedside skips the ring prewarm while muted. See the `muteRingtone` section of `docs/call-broadcast-announce.md`.

- Rebuilt the sherpa NAPI shim from source and put that source in the repo. `sherpa_tts_napi.cpp` had never been committed — only the `libs/armeabi-v7a/libsherpa_onnx.so` artifact and a sha256 that no longer matched the shipped file (`48fd705d…` recorded, `62ca9394…` actual) — so when the `dataDir` field was needed for `matcha-icefall-zh-en` there was nothing on this machine to edit. The rewrite keeps the exported surface identical (`create/createAsync/destroy/generate/generateAsync/sampleRate/numSpeakers`, module name `sherpa_onnx`, tag `SherpaShim`, handles are index+1 so `0` still means "no engine"), adds the optional `dataDir` (the `espeak-ng-data` directory itself, not its parent — sherpa probes `<data_dir>/phontab`, required for any Chinese+English model to voice Latin letters), and is now built by `tools/build-sherpa-shim.sh`. Two traps are recorded in `docs/tts-models-and-native-build.md`: do not pass `-nostdlib++` (the typeinfo/vtable relocations resolve at load time, before the constructor's `dlopen` can help), and the struct field order must track sherpa-onnx **v1.12.18** `c-api.h:1019-1100`.
